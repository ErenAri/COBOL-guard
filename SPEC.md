# COBOL Guard Specification

## 1. Objective

COBOL Guard proves that a modernization candidate preserves legacy behavior under strict, auditable controls.

`v1` is the COBOL oracle.  
`v2` is the Python candidate service.

Oracle execution modes:
- `python-reference` (local deterministic mode)
- `cobol-command` / `cobol-executable` (external command contract using input JSONL and output JSON artifacts)

## 2. Scope

Supported operations:
- `POST`
- `REVERSE`
- `BALANCE`
- `RECONCILE`

Outputs:
- ledger journal
- reconcile totals report
- exception report

Out of scope:
- FX
- settlement lifecycle
- overdraft policies
- fee engines

## 3. Domain Contract

### POST
- Input: `request_id`, `account_id`, `amount_cents:int64`, `business_date`, `event_time`
- Behavior: idempotent by `request_id`

### REVERSE
- Input: `reverse_request_id` (`request_id` field), `original_request_id`, `account_id`, `business_date`, `event_time`
- Behavior:
- `original_request_id` must reference an existing applied `POST`
- idempotent by `reverse_request_id`

### BALANCE
- Returns current account balance in cents.

### RECONCILE
- Computes total posted, total reversed, net delta, closing total, and exceptions.

## 4. Money Model

- Money is represented as `int64` cents in COBOL and Python.
- Floating-point arithmetic is prohibited in rule paths.
- Decimal parsing/formatting is allowed only at external boundaries.

## 5. Schema Registry Rules

Schema registry is the single source of truth for:
- field layout
- canonicalization
- compatibility policy
- deterministic sorting

Each schema must include:
- `schema_id`
- `version`
- `record_layout`
- `encoding_spec`
- `primary_key_fields`
- `canonical_sort_key_fields`
- `record_fingerprint_fields`
- `money_fields`
- `nullability_defaults`
- `canonicalization_spec_version`
- `canonical_byte_encoding_rules`
- `compatibility_policy`
- `hash_algorithm_version`

## 6. Canonicalization Rules

`canonical_record_bytes` are defined by:
1. materialize null/default values first
2. serialize fields in `record_layout` order
3. apply schema-defined padding/truncation/formatting
4. encode as UTF-8 (no BOM)

For `int64` cents:
- fixed width
- leading sign (`+` or `-`) for signed fields
- zero padded digits

Record fingerprint:
- `sha256(schema_version + canonical_record_bytes)`

Sorting:
1. `canonical_sort_key_fields`
2. `primary_key_fields`
3. `record_fingerprint`

## 7. Determinism Controls

- Locale pinned to `C`
- Bytewise collation
- Newline pinned to LF
- Frozen clock in deterministic test mode
- Single writer per account partition
- Deterministic batch chunking and merge ordering

Run manifest must include:
- schema versions
- code version
- dataset seed id
- benchmark profile id
- deterministic mode flags

## 8. Batch Restartability

Unit of work:
- `account_id + business_date`

Checkpointing:
- chunk checkpoints with unit-of-work cursor
- temporary output write
- manifest validation
- atomic promote
- restart skips committed chunks
- inflight marker detection and explicit rework chunk accounting on resume

Dedup keys:
- transaction replay: `(run_id, request_id)`
- batch replay: `(run_id, record_fingerprint)`

## 9. Invariants

1. Conservation: `opening + posts - reversals = closing`
2. Idempotency: duplicate request id does not change net state
3. Reversal law: reversing a posted request neutralizes prior effect
4. Reconcile consistency: journal net delta equals reconcile net delta
5. Determinism: same manifest produces identical output hashes

## 10. Severity Mapping

From `governance/gate_policy.yml`:
- `BLOCKER`: diffs in `money_fields`, `balance_after_cents`, reconcile totals
- `CRITICAL`: diffs in `status`, `audit_event`
- `MAJOR`: schema mismatch, missing records, ordering failure after canonical sort
- `MINOR`: non-semantic metadata-only diffs

## 11. Blast Radius Control

Default threshold:
- `changed_records_ratio <= 0.1%`

Above threshold requires:
- `change_class: intended_behavior_change`
- explicit override rationale
- two-person signed approval

## 12. Re-Bless and Promotion Policy

- Candidate and locked baselines are separate.
- Promotion requires:
1. passing release gates
2. two valid Ed25519 signatures
3. approver public keys present in `governance/keys/`
4. mandatory rationale metadata
5. signing mode recorded (`ed25519-pem` or `kms-command`)

Manifest must include:
- commit SHA
- schema versions
- harness version
- case id
- run id
- change class
- ticket
- risk statement
- policy version and hash
- workflow run id
- environment
- provenance ref
- KMS key version metadata when `kms-command` mode is used

## 13. Benchmark and Performance Gates

- Benchmark report is generated by harness CLI and includes:
- candidate transaction throughput and latency (`tps`, `p95_ms`, `p99_ms`)
- batch throughput (`records_processed`, `duration_seconds`)
- restart resilience (`restart_rework_chunks`)
- Verify can enforce these gates when benchmark evidence is supplied.

## 14. Evidence Pack Integrity

- Evidence packs include:
- retention class
- immutability proof reference
- provenance reference
- policy version
- environment and workflow run id

- `verify-evidence-pack` validates:
1. manifest signatures against required signer ids
2. minimum valid signature count
3. every listed file hash/size
4. unexpected content files
